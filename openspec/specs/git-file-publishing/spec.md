# Git 逐文件提交推送

## Purpose

定义 JchTools 的Git 逐文件提交推送及其可观察结果、约束、例外和验收边界。只负责逐文件提交推送及其保护、合并、重试和停止；同时适用全局界面、错误约束与共用附录 E，完整条文与附录同时满足，示例不覆盖明文规则。

各能力同时遵守[应用全局与共用规格](../application-contract/spec.md)，工程纪律见[AGENTS.md](../../../AGENTS.md)。本文为已批准需求，不记录实现状态或测试通过状态；未实现不撤销要求，历史授权不授予当前执行权限。

## Requirements

<a id="4-git-工具g"></a>

**4. Git 工具（G）**

本工具是现有工具箱的新增独立工具（H-03 / G-01），通过 Windows 中用户已安装的系统 Git 对用户指定的本地仓库执行逐文件提交并推送；其网络访问范围按 P-03 的 Git 工具例外执行，配置与系统 Git 完全一致（G-17）。

### Requirement: G-01

JchTools MUST 遵守本条行为：功能范围与导航：保留工具箱现有全部功能，在现有左侧导航中新增「Git 工具」导航项；点击进入 Git 工具页面。

#### Scenario: G-01 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 功能范围与导航：保留工具箱现有全部功能，在现有左侧导航中新增「Git 工具」导航项；点击进入 Git 工具页面。当前 Git 工具只实现「逐文件提交并推送」一个功能，不提供分支管理、Tag、Git GUI、Commit 浏览、Clone、Pull 工具、Reset、Rebase GUI 或其他任何 Git 功能。仅使用 Windows 中用户已安装、由系统 `PATH` 按原有顺序解析到的 Git for Windows（`git.exe`），不固定 Git 版本，不从程序目录或所选仓库查找替代版本。安装包和便携 ZIP 均不随附 Git 及其运行组件，JchTools 不下载、安装或初始化 Git；找不到或无法运行系统 Git 时，明确提示用户安装 Git 并使其在 `PATH` 中可用，禁止启动本次 Git 任务，但不阻塞其他工具。配置与认证行为按 G-17 原样继承，不因调用系统 Git 扩张网络或任务范围。（系统 Git 来源于 2026-10-13 用户确认）

### Requirement: G-03

JchTools MUST 遵守本条行为：核心原则（严格串行）：必须按「一个文件 → 单独 git add → 单独 commit → 单独 push → push 成功 → 才处理下一个文件」执行。

#### Scenario: G-03 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 核心原则（严格串行）：必须按「一个文件 → 单独 git add → 单独 commit → 单独 push → push 成功 → 才处理下一个文件」执行。任何时刻只能处理一个文件，禁止并发；禁止「文件 A commit、文件 B commit、文件 C commit、最后统一 push」的批量模式，必须是每个文件 commit 后立即 push、push 成功后才进入下一个文件。

### Requirement: G-04

JchTools MUST 遵守本条行为：变更类型：处理新增、修改、删除、重命名四类变更；Git 已识别的 rename 作为一个逻辑变更处理（一次 commit + 一次 push，不拆成删除与新增两次）。

#### Scenario: G-04 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 变更类型：处理新增、修改、删除、重命名四类变更；Git 已识别的 rename 作为一个逻辑变更处理（一次 commit + 一次 push，不拆成删除与新增两次）。每个逻辑文件变更单独 commit + push。

### Requirement: G-05

JchTools MUST 遵守本条行为：单文件 commit 验证（硬性要求）：每次 commit 必须验证该 commit 只包含当前正在处理的文件变更（rename 为新旧两个路径），不得因为暂存区里已有其他文件而一次提交多个文件；验证失败时立即停止自动操作并显示具体原因。

#### Scenario: G-05 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 单文件 commit 验证（硬性要求）：每次 commit 必须验证该 commit 只包含当前正在处理的文件变更（rename 为新旧两个路径），不得因为暂存区里已有其他文件而一次提交多个文件；验证失败时立即停止自动操作并显示具体原因。

### Requirement: G-06

JchTools MUST 遵守本条行为：保护现有 staged 状态：用户启动工具前可能已执行过 git add，仓库可能已存在 staged 文件。

#### Scenario: G-06 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 保护现有 staged 状态：用户启动工具前可能已执行过 git add，仓库可能已存在 staged 文件。工具必须保护现有工作区和暂存区：不得删除用户 staged 内容、不得 reset 用户修改、不得 checkout 覆盖用户代码、不得 clean 用户文件、不得把其他 staged 文件带入当前 commit。必须使用安全方式（按路径限定提交范围的 git 机制）确保每次 commit 只包含当前文件。如果仓库当前状态无法安全保证这一点（如处于未完成的 merge、rebase 等中间态），不得冒险继续，停止自动操作并在界面显示具体原因。

### Requirement: G-07

JchTools MUST 遵守本条行为：Commit Message 格式：每个文件的提交信息固定为 `update: <相对路径>`，其中路径必须是相对于 Git 仓库根目录的路径（分隔符统一 `/`），全部提交统一采用这一格式；rename 的提交信息使用新路径。

#### Scenario: G-07 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件

### Requirement: G-08

JchTools MUST 遵守本条行为：Push：正常情况下使用当前分支已经配置好的 upstream 执行 `git push`（不带额外远程或分支参数）。

#### Scenario: G-08 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** Push：正常情况下使用当前分支已经配置好的 upstream 执行 `git push`（不带额外远程或分支参数）。当前文件只有在 push 成功之后才算完成，然后才能进入下一个文件。

### Requirement: G-09

JchTools MUST 遵守本条行为：失败重试：git add、git commit、git push 任一步出现可重试失败时，不得跳过当前文件，使用无限重试；退避策略为第 1 次失败等待 5 秒、第 2 次 10 秒、第 3 次 20 秒、第 4 次 40 秒、第 5 次及以后每次 80 秒，一直重试当前文件的当前阶段直到成功或用户手动停止，不得因达到固定次数自动跳过当前文件。

#### Scenario: G-09 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 失败重试：git add、git commit、git push 任一步出现可重试失败时，不得跳过当前文件，使用无限重试；退避策略为第 1 次失败等待 5 秒、第 2 次 10 秒、第 3 次 20 秒、第 4 次 40 秒、第 5 次及以后每次 80 秒，一直重试当前文件的当前阶段直到成功或用户手动停止，不得因达到固定次数自动跳过当前文件。重试按阶段记忆：commit 已成功后 push 失败的，只重试 push，不重复 commit。

### Requirement: G-10

JchTools MUST 遵守本条行为：远端新提交自动处理：git push 因远端 branch 已有新提交（如 non-fast-forward、fetch first、rejected）失败时，自动拉取当前 upstream 最新提交并按正常 merge 语义合并到当前本地 branch（不擅自 rebase、不改写历史），合并成功后继续 push，push 成功后才能继续下一个文件。

#### Scenario: G-10 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 远端新提交自动处理：git push 因远端 branch 已有新提交（如 non-fast-forward、fetch first、rejected）失败时，自动拉取当前 upstream 最新提交并按正常 merge 语义合并到当前本地 branch（不擅自 rebase、不改写历史），合并成功后继续 push，push 成功后才能继续下一个文件。合并被本地未提交变更阻挡而无法进行时，停止自动操作并显示具体原因。对 `assume-unchanged` / `skip-worktree` 隐藏的本地修改，若远端更新会涉及其路径，必须在触发可能覆盖这些内容的不安全 merge 前检测并停止，保留原有工作区内容及索引标记；不得等 merge 失败后才核对并以事后内容等于索引推断没有阻挡，不得为检测清除或改写这些标记，也不得将这些隐藏修改纳入逐文件提交清单。内容判定必须按 G-17 尊重既有 filters / EOL 行为，不通过覆盖配置或改写文件消除差异；此保护不改变其他安全合并、重试及成功路径，实际冲突仍按 G-11 处理。

### Requirement: G-11

JchTools MUST 遵守本条行为：冲突停止：自动合并出现 conflict 时必须停止自动操作：程序不得自行选择 ours 或 theirs，不得自动覆盖任何一方内容，保留 Git 冲突现场；用户已有的合并策略仍按 G-17 原样生效，不由 JchTools 清除或覆盖。

#### Scenario: G-11 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 冲突停止：自动合并出现 conflict 时必须停止自动操作：程序不得自行选择 ours 或 theirs，不得自动覆盖任何一方内容，保留 Git 冲突现场；用户已有的合并策略仍按 G-17 原样生效，不由 JchTools 清除或覆盖。界面显示存在 merge conflict、冲突文件、Git 输出、当前处理文件与当前操作阶段，等待用户在外部或后续交互中解决冲突；用户解决完成（仓库不再有未合并条目）后允许继续当前任务——若合并尚未提交，工具自动完成合并提交（不做额外改动）后继续 push。

### Requirement: G-12

JchTools MUST 遵守本条行为：失败状态恢复：以 Git 本身作为实际状态来源：重新扫描仓库时只处理当前仍然存在的未提交变更；已经 commit + push 成功且工作区不再显示对应变更的文件不得再次提交。

#### Scenario: G-12 完整行为与适用边界
- **WHEN** 用户通过 Git 工具处理所选仓库的逐文件提交与推送，且涉及本条规定的条件
- **THEN** 失败状态恢复：以 Git 本身作为实际状态来源：重新扫描仓库时只处理当前仍然存在的未提交变更；已经 commit + push 成功且工作区不再显示对应变更的文件不得再次提交。不为跟踪进度额外创建没有必要的永久状态数据库。扫描优先使用 git 自身的状态信息获取变更文件，不做没有必要的深度文件遍历。

JchTools MUST 遵守本条行为：界面信息：界面必须实时显示足够详细的执行信息，至少包括：仓库路径、当前 branch、upstream、待处理文件总数、已完成文件数、当前文件、当前阶段、当前重试次数、下一次重试等待时间、总体状态。

#### Scenario: G-13 完整行为与适用边界

### Requirement: G-14

JchTools MUST 遵守本条行为：详细日志：Git 工具界面提供实时日志区域，必须显示实际执行阶段、Git stdout、Git stderr、错误原因、push 返回内容、merge 返回内容、retry 信息与成功信息；日志便于用户判断当前卡在 add、commit、push、网络、认证、远端更新、merge conflict 还是其他 Git 错误，不得只显示「失败」这类无诊断价值的信息。

### Requirement: G-15

JchTools MUST 遵守本条行为：停止操作：Git 长时间自动重试时用户必须能够主动停止。

#### Scenario: G-15 完整行为与适用边界

### Requirement: G-16
