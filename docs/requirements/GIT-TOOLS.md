# Git 工具需求（G）

本文唯一维护逐文件提交并推送及相应保护、合并、重试与停止行为。全局联网、代理及界面约束见 [CONTRACT.md](CONTRACT.md)，其附录 E 保留本域的边界期望；开发纪律见 [../../AGENTS.md](../../AGENTS.md)。本文不记录实现或测试状态。

## 4. Git 工具（G）

本工具是现有工具箱的新增独立工具（H-03 / G-01），通过随包 Git 运行组件对用户指定的本地仓库执行逐文件提交并推送；其网络访问范围按 P-03 的 Git 工具例外执行。

- **G-01** 功能范围与导航：保留工具箱现有全部功能，在现有左侧导航中新增「Git 工具」导航项；点击进入 Git 工具页面。当前 Git 工具只实现「逐文件提交并推送」一个功能，不提供分支管理、Tag、Git GUI、Commit 浏览、Clone、Pull 工具、Reset、Rebase GUI 或其他任何 Git 功能。两种发布形态均随附官方来源及固定清单校验的 Portable Git 完整运行组件和许可材料，优先从程序目录使用，无需用户另装 Git；保留已有 Git 配置和认证行为，不因内置组件扩张网络或任务范围。

- **G-02** 输入验证：用户输入或选择一个本地 Git 项目目录。开始之前至少验证：目录存在、是有效 Git repository、当前存在检出的 branch、当前 branch 已配置 upstream；任一不满足时明确报错并禁止开始。使用当前 branch 与其已配置的 upstream，不自动切换 branch，不自动修改 remote 配置。

- **G-03** 核心原则（严格串行）：必须按「一个文件 → 单独 git add → 单独 commit → 单独 push → push 成功 → 才处理下一个文件」执行。任何时刻只能处理一个文件，禁止并发；禁止「文件 A commit、文件 B commit、文件 C commit、最后统一 push」的批量模式，必须是每个文件 commit 后立即 push、push 成功后才进入下一个文件。

- **G-04** 变更类型：处理新增、修改、删除、重命名四类变更；Git 已识别的 rename 作为一个逻辑变更处理（一次 commit + 一次 push，不拆成删除与新增两次）。每个逻辑文件变更单独 commit + push。

- **G-05** 单文件 commit 验证（硬性要求）：每次 commit 必须验证该 commit 只包含当前正在处理的文件变更（rename 为新旧两个路径），不得因为暂存区里已有其他文件而一次提交多个文件；验证失败时立即停止自动操作并显示具体原因。

- **G-06** 保护现有 staged 状态：用户启动工具前可能已执行过 git add，仓库可能已存在 staged 文件。工具必须保护现有工作区和暂存区：不得删除用户 staged 内容、不得 reset 用户修改、不得 checkout 覆盖用户代码、不得 clean 用户文件、不得把其他 staged 文件带入当前 commit。必须使用安全方式（按路径限定提交范围的 git 机制）确保每次 commit 只包含当前文件。如果仓库当前状态无法安全保证这一点（如处于未完成的 merge、rebase 等中间态），不得冒险继续，停止自动操作并在界面显示具体原因。

- **G-07** Commit Message 格式：每个文件的提交信息固定为 `update: <相对路径>`，其中路径必须是相对于 Git 仓库根目录的路径（分隔符统一 `/`），全部提交统一采用这一格式；rename 的提交信息使用新路径。

- **G-08** Push：正常情况下使用当前分支已经配置好的 upstream 执行 `git push`（不带额外远程或分支参数）。当前文件只有在 push 成功之后才算完成，然后才能进入下一个文件。

- **G-09** 失败重试：git add、git commit、git push 任一步出现可重试失败时，不得跳过当前文件，使用无限重试；退避策略为第 1 次失败等待 5 秒、第 2 次 10 秒、第 3 次 20 秒、第 4 次 40 秒、第 5 次及以后每次 80 秒，一直重试当前文件的当前阶段直到成功或用户手动停止，不得因达到固定次数自动跳过当前文件。重试按阶段记忆：commit 已成功后 push 失败的，只重试 push，不重复 commit。

- **G-10** 远端新提交自动处理：git push 因远端 branch 已有新提交（如 non-fast-forward、fetch first、rejected）失败时，自动拉取当前 upstream 最新提交并按正常 merge 语义合并到当前本地 branch（不擅自 rebase、不改写历史），合并成功后继续 push，push 成功后才能继续下一个文件。合并被本地未提交变更阻挡而无法进行时，停止自动操作并显示具体原因。

- **G-11** 冲突停止：自动合并出现 conflict 时必须停止自动操作：不得自动选择 ours 或 theirs，不得自动覆盖任何一方内容，保留 Git 冲突现场。界面显示存在 merge conflict、冲突文件、Git 输出、当前处理文件与当前操作阶段，等待用户在外部或后续交互中解决冲突；用户解决完成（仓库不再有未合并条目）后允许继续当前任务——若合并尚未提交，工具自动完成合并提交（不做额外改动）后继续 push。

- **G-12** 失败状态恢复：以 Git 本身作为实际状态来源：重新扫描仓库时只处理当前仍然存在的未提交变更；已经 commit + push 成功且工作区不再显示对应变更的文件不得再次提交。不为跟踪进度额外创建没有必要的永久状态数据库。扫描优先使用 git 自身的状态信息获取变更文件，不做没有必要的深度文件遍历。

- **G-13** 界面信息：界面必须实时显示足够详细的执行信息，至少包括：仓库路径、当前 branch、upstream、待处理文件总数、已完成文件数、当前文件、当前阶段、当前重试次数、下一次重试等待时间、总体状态。当前阶段至少区分：扫描、add、commit、push、pull/fetch、merge、等待重试、冲突、完成。

- **G-14** 详细日志：Git 工具界面提供实时日志区域，必须显示实际执行阶段、Git stdout、Git stderr、错误原因、push 返回内容、merge 返回内容、retry 信息与成功信息；日志便于用户判断当前卡在 add、commit、push、网络、认证、远端更新、merge conflict 还是其他 Git 错误，不得只显示「失败」这类无诊断价值的信息。

- **G-15** 停止操作：Git 长时间自动重试时用户必须能够主动停止。停止后：不继续处理新的文件、不启动下一次 retry、不强行回滚已经成功的 commit、不破坏当前 Git repository 状态；已经成功 commit + push 的文件保持成功状态。正在执行的 git 命令等待其自然结束后不再启动后续操作。

- **G-16** 进度：界面至少显示「已完成 / 总数」（如 `38 / 120`）；每完成一个文件的 commit + push 后更新一次完成数；失败并正在 retry 的当前文件不得算入已完成数量。
